Model catalogue

A public catalogue row must identify a reusable EO foundation model, model family, released framework, or model artifact. Survey papers and generic downstream methods are excluded.

Benchmarks

Benchmark suites, pre-training datasets, embedding datasets, and evaluation resources are separated from models so the model landscape is not polluted by datasets.

Versioning

New releases such as a 1.5 model are treated as versioned candidates. They should inherit the model-family identity but keep distinct paper, weights, date, capability, and benchmark evidence.

Public quality

The site should not publish placeholders as scientific claims. Missing exact values are represented by derived public text, provenance fields, and candidate reports rather than vague table copy.

Landscape

The default map uses modality complexity on the X-axis and an atlas evidence score on the Y-axis. The evidence score spreads models by task/evaluation breadth, modalities, architecture detail, access, and source links.

Submissions

Public submissions enter the same candidate pipeline. They need primary-source links before they should change the public catalogue.

Public website policy

What gets published

  • Canonical model or benchmark name
  • Original paper, DOI, arXiv, or project page
  • Official code, model card, weights, or dataset link when available
  • Modalities, sensors, architecture family, and modelling paradigm
  • Downstream tasks inferred from source evidence or recorded explicitly
  • Access status based on paper/code/weights availability
  • Publication report explaining included and excluded records

Better automation

How new public releases should be handled

Source monitors

Monitor configured upstream lists plus arXiv, GitHub, Hugging Face, and public submissions. The discovery-source configuration defines these channels, but every candidate still needs a primary paper, repository, model card, project page, or release note before publication.

Version-aware matching

Store model-family keys separately from release IDs. For a release such as OLMoEarth 1.5, the automation should link it to the OLMoEarth family while preserving the version-specific paper, weights, capabilities, and evaluation claims.

Evidence thresholds

Auto-publish only when strong evidence exists. Otherwise, keep the item in candidate reports. The public site can show latest stable rows while maintainers review ambiguous records.

Audit trail

Each build writes raw snapshots, parsed records, candidate JSON, validation reports, and a publication report. That makes every public row traceable back to upstream evidence.
